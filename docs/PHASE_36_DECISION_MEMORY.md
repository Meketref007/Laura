# Phase 36 — Decision Memory Integration

Summary
-------

Phase 36 integrates the decision execution flow with the semantic memory so that outcomes generated by the `DecisionEngine` are persisted as `DecisionOutcome` entries and indexed in the configured vector store (in-memory, Annoy, or Faiss).

Main points
-----------

- `DecisionExecutor` now accepts an optional `engine: DecisionEngine`. After a successful execution it notifies the engine which records an outcome via `MemoryLayer.remember_outcome_with_vector` when an embedder is available.
- Vector indexing is pluggable: use `InMemoryVectorStore`, `Annoy` or `Faiss` via the existing CLI flags (`--vector-backend`, `--faiss-index-path`, `--faiss-meta-path`).
- A sidecar `reports/decision_vectors.jsonl` persists vectors for durability and reindex operations.

CLI / Developer Examples
------------------------

Reindex decisions into the chosen backend (example for `faiss`):

```bash
# Reindex JSONL sidecar into Faiss index
python -m shopee_agent.cli memory-reindex-vectors --vector-backend faiss --faiss-index-path reports/faiss.index --faiss-meta-path reports/faiss.meta
```

Semantic search against decision memory (in-memory example):

```bash
python -m shopee_agent.cli memory-semantic-search --vector-backend memory --query "pricing margin drop"
```

Testing
-------

- Integration test `tests/test_decision_executor_integration.py` validates the full path: executor → engine.execute_decision → MemoryLayer + vector indexing.

Why this matters
----------------

Persisting outcomes with vectors enables:

- Case-based reasoning via semantic similarity queries
- Faster retrieval for decision auditing and learning
- Offline reindexing and migration between backends (sidecar files enable rebuilding indexes)

Next steps
----------

- Add CLI option to enable/disable immediate index persistence for large-scale deployments.
